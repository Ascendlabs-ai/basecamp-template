# Provisioning the database

Two SQL files, applied in order, then one INSERT to create the first
administrator. Nothing else.

| File | What it is |
|---|---|
| `migrations/0001_baseline.sql` | The whole schema: tables, enums, functions, policies, triggers, grants. Generated by `pg_dump --schema-only --no-owner`; contains **no rows**. |
| `migrations/0002_security_boundary.sql` | Hand-written. Pins ownership, hardens the definer functions, and **asserts** the boundary rather than describing it. |

> **On the filenames.** These are numbered `0001`/`0002` rather than carrying the
> Supabase CLI's 14-digit timestamps, because they are applied once at
> provisioning through the SQL Editor or `psql` — not pushed with
> `supabase db push`. If you would rather manage them with the CLI, rename them
> to timestamped form first.

---

## Order of operations

### 0. Expose the `basecamp` schema to the Data API — do this first

Supabase Dashboard → **Project Settings → API → Exposed schemas**. Add
`basecamp` alongside whatever is already listed.

This is a project setting, not schema DDL, so `pg_dump` cannot carry it and no
migration can set it. Skip it and PostgREST answers `PGRST106` for every
request — the app renders an error and nothing in the database looks wrong,
which is a genuinely difficult failure to diagnose from the outside.

The field is replaced wholesale when edited. **Add** `basecamp`; never remove an
existing entry.

### 1. Apply the two files, in order

SQL Editor, or `psql "$DATABASE_URL" -f …`. `0002` ends by asserting the whole
security boundary, so if it commits without raising, the boundary holds:

- every `basecamp` table is owned by `postgres`, has RLS on, and does not have
  FORCE RLS (which would make the definer helpers recurse against their own
  policies);
- every SECURITY DEFINER function is `postgres`-owned, has `search_path` pinned
  empty, and is not executable by `PUBLIC`;
- `anon` holds nothing anywhere in the schema, and no policy names `anon` or
  `public`;
- `authenticated` *can* reach the schema and read `basecamp.entries` — the
  check that catches an install which would otherwise fail
  `permission denied for schema basecamp` on every request;
- `authenticated` holds **no write** on `basecamp.super_admins`, and
  `service_role` holds neither UPDATE nor TRUNCATE on it — an UPDATE would
  reassign the roster without changing the row count, so the last-row guard
  would never fire;
- both trust-root guards exist **and are enabled** (a disabled trigger keeps its
  definition, so asserting the source text would prove nothing);
- no view in `basecamp` runs with owner rights — since PG15 a view without
  `security_invoker` reads straight past RLS.

### 2. Create the administrator's account

Dashboard → **Authentication → Users → Add user**. This app has no self-signup.

### 3. Insert their trust-root row

There is **no bootstrap function**. This is a deliberate, attributed INSERT:

```sql
insert into basecamp.super_admins (user_id, note)
select u.id, 'first administrator, provisioned at install'
  from auth.users u
 where u.email = 'PUT-THE-ADMIN-EMAIL-HERE'
on conflict (user_id) do nothing;
```

Run it in the SQL Editor, which connects as `postgres` — so RLS does not apply
and no policy can refuse it.

**Why not an RPC that promotes whoever calls it first?** Because that is a
security decision with no operator in the loop and no attribution: the row would
record "the first signed-in account claimed it", not who decided or why. It also
saves exactly one statement in a flow that already requires the dashboard twice.
The cost of doing it this way is real — it is a hand-edited SQL statement in
every install — which is why step 4 exists.

### 4. Verify before you trust it

`cp .env.local.example .env.local`, fill in the two values, `npm run dev`, sign
in as that account, and confirm **`/admin/access` renders the administration
screen** rather than the locked panel.

The install is not complete until you have seen that. The locked panel is what
the screen looks like when the database says you are not an administrator — it
is a consequence of the policy answer, not a separate check, so seeing the real
screen is the only proof the trust root took.

### 5. Build your catalog

Categories and entries are `super_admin`-only writes, enforced by policy. There
is no catalog-editing UI in this template yet; add rows with SQL, or build the
screen — the write policies are already correct.

Start from **`supabase/seed.example.sql`**: 4 categories and 12 entries covering
all three entry types and a spread of statuses, with the non-obvious constraints
(the slug regex, the launchable-needs-a-URL rule, the nav_group restriction)
written out at the top. Run it, click around, then delete the rows and write
your own. It is idempotent, so re-running it is a no-op.

Note that after seeding you will see the catalog only because you are a
super_admin. A colleague with no grants sees nothing until you grant them
something in `/admin/access` — that is the access model working.

## Administering the roster afterwards

**Also SQL Editor work, for now.** `basecamp.super_admins` carries INSERT and
DELETE *policies* gated on `is_super_admin()`, but `authenticated` is granted
**SELECT only**. The roster is therefore not self-administering through the API.

That is deliberate: granting internet-reachable writes on the trust root before
anything consumes them is unnecessary attack surface. Add the privileges in
whichever migration ships the admin panel that uses them; the policies are
already written and correct for that day.

Add an administrator:

```sql
insert into basecamp.super_admins (user_id, note)
select u.id, 'promoted by <you>, <date>, <reason>'
  from auth.users u
 where u.email = 'THEIR-EMAIL-HERE'
on conflict (user_id) do nothing;
```

Remove one:

```sql
delete from basecamp.super_admins where user_id = 'THEIR-UUID-HERE';
```

Two floors protect the table, and both refuse rather than warn:

- **The last row cannot be deleted.** A `BEFORE DELETE` row trigger raises, and
  the exception aborts the whole statement — so even
  `delete from basecamp.super_admins` leaves *every* row intact, not one.
  Promote a replacement before demoting the last administrator.
- **`TRUNCATE` is refused outright.** A `BEFORE TRUNCATE` statement trigger
  raises unconditionally, because `BEFORE DELETE` triggers do not fire on
  TRUNCATE — the delete guard alone would have left the table emptiable in one
  word.

If a dashboard user-deletion fails with
`23503 … basecamp_super_admins_user_id_fkey`, that is the foreign key refusing
on purpose: the account is an administrator. Demote them first.

## If you lock yourself out

Every admin capability is gated by `basecamp.is_super_admin()`, all access is
RLS, and the app holds only an anon key. There is no service-role escape hatch
and no server-side role check — so if that function stops returning true for
everyone, there is **no way back in from inside the app**.

The way back in is the SQL Editor, which runs as `postgres`:

```sql
-- Who is currently an administrator?
select u.email, s.note, s.created_at
  from basecamp.super_admins s
  join auth.users u on u.id = s.user_id
 order by u.email;

-- Restore one by email.
insert into basecamp.super_admins (user_id, note)
select u.id, 'lockout recovery'
  from auth.users u
 where u.email = 'PUT-THE-ADMIN-EMAIL-HERE'
on conflict (user_id) do nothing;

-- What does the gate actually read?
select prosrc from pg_proc p
  join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'basecamp' and p.proname = 'is_super_admin';
```

Calling `basecamp.is_super_admin()` bare in the editor proves nothing — it runs
as `postgres`, `auth.uid()` is null, and it returns false for reasons unrelated
to whether your administrators can get in. To ask the question *as* someone,
highlight both of these and run them together:

```sql
select set_config('request.jwt.claims',
  '{"sub":"THEIR-UUID-HERE","role":"authenticated"}', true);
select basecamp.is_super_admin() as must_be_true;   -- last, so you can see it
```

Two details that matter. Put the `is_super_admin()` call **last**: the SQL
Editor renders only the final statement's result grid, so a trailing reset
statement would hide the very answer you are after. And pass `true` as the third
argument — a multi-statement submission runs as one implicit transaction, so a
transaction-local setting both works and reverts itself on commit. `false` would
leave a spoofed identity on a pooled backend after the transaction ends.

This proves the gate's LOGIC while connected as `postgres`. It does not prove
that the `authenticated` role can reach the schema — the exposure step and a
real sign-in are what prove that.
